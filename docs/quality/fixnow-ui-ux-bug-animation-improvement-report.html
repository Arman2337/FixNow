Executive summary

Strong foundations, unsafe edges

The app has a strong design source, shared state primitives, clear booking states and useful offline/error language. The highest risk is not visual polish. It is that a number of high-value actions are visible but not actually connected to their workflows, while some operational screens present synthetic or stale facts as live truth.

What is working

  • Shared mobile empty, error, offline, skeleton and button states exist.
  • Booking lifecycle, realtime client, tracking freshness and provider controllers have explicit state models.
  • Admin uses semantic tables, visible focus, permission-aware navigation and honest empty-state copy in several queues.
  • Motion tokens already support press feedback, skeletons, map movement and provider acceptance.

What needs attention

  • No-op controls and simulated success are visible in customer tracking, bookings, support, provider requests and admin auth.
  • Trust, ETA, KYC, earnings and operational metrics sometimes use fallback or hardcoded values.
  • Customer and provider navigation drift from DESIGN.md.
  • Admin has no route-level loading/error boundaries and a fixed sidebar on small widths.

How to read this report

  • Confirmed means directly supported by source or a command result in this audit.
  • Static means the behavior is visible in code but needs runtime/device reproduction.
  • Suggestion is a product or design recommendation, not a claimed bug.
  • Possible is a risk requiring production or device evidence.

UI/UX review

Experience issues and design drift

These are the highest-value experience improvements. Several are also functional defects and are cross-referenced in the bug register.

UX-01 · One visible action does nothing

P0

Customer tracking exposes Reschedule and Cancel Booking, and Customer Bookings exposes Schedule New Service. Reschedule has an empty callback, Cancel only shows a success-looking message, and Schedule New Service only tries to pop the current route.

Problem

Users can make a high-consequence decision and receive no actual state change.

Suggested fix

Connect each action to one controller command, confirmation and recovery state. If a control is unavailable, hide it or disable it with a reason.

User benefit

Booking state stays trustworthy and the user always knows whether the server accepted the action.

Before

Tap “Cancel Booking” → green message says cancellation initiated.

Tap “Reschedule” → nothing happens.

After

Tap Cancel → reason and consequence dialog → pending state → confirmed/cancelled state with timestamp.

Tap Reschedule → availability sheet → explicit confirmation.

Static evidence: mobile/lib/features/tracking/booking_tracking_screen.dart:755-881, mobile/lib/features/bookings/customer_bookings_screen.dart:304-331.

UX-02 · Provider navigation does not match the operating model

P1

The provider tab bar shows Home, Active Job, History and Profile. The design contract specifies Home/Jobs, Active Job, Earnings and Profile. The verified provider Profile destination is also implemented by the applicant onboarding screen.

Problem

High-value money, job and identity contexts compete in the wrong place.

Suggested fix

Use the four destinations from DESIGN.md, keep Active Job state persistent, and create a read-only profile mode for verified providers.

User benefit

Providers can find earnings, active work and account controls with less scanning.

Source: mobile/lib/app/app_navigation.dart:42-63, mobile/lib/app/app.dart:571-595; contract: DESIGN.md:251-260.

UX-03 · Fixed admin navigation breaks small-screen use

P1

AdminShell fixes a 288px sidebar and applies pl-72. There is no narrow-screen drawer, collapse control or alternate mobile navigation.

Problem

At smaller laptop or tablet widths, content is pushed sideways and dense tables become the only navigation pattern.

Suggested fix

Collapse the sidebar below the admin breakpoint, retain a labelled menu button, reserve header height, and provide a mobile card/list mode for operational rows.

User benefit

Administrators can work from smaller screens without losing sections or creating horizontal reading traps.

Before

288px fixed sidebar + 288px content offset at every viewport width.

After

Desktop: collapsible labelled rail. Small screen: menu button + stacked sections + card/list fallback for tables.

Source: admin/src/components/admin-shell.tsx:21-21, admin/src/components/admin-shell.tsx:76-109; responsive requirement: DESIGN.md:441-445.

UX-04 · The mobile visual system is not the approved system

P1

The design source calls for a premium dark authenticated system using Playfair Display and Inter. Flutter uses Manrope, and AppTheme.dark copies the light theme before changing only a few surface values.

Problem

Dark-mode contrast, heading hierarchy and screen-to-screen consistency cannot be guaranteed when semantic tokens are inherited from light mode.

Suggested fix

Create a complete dark semantic token set, load the intended font assets, and remove screen-level hardcoded colors. Validate contrast independently.

User benefit

Customers and providers get a calmer, more legible interface with predictable hierarchy.

Contract: DESIGN.md:62-109, DESIGN.md:90-95. Implementation: mobile/lib/design_system/app_theme.dart:8-48, mobile/lib/design_system/app_theme.dart:210-221, mobile/lib/design_system/app_typography.dart:5-19, mobile/pubspec.yaml:47-60.

UX-05 · Provider job cards are not resilient to content size

P0

Provider job card rows use natural-size children inside a horizontal Row, and a nested InkWell appears in a widget test without a Material ancestor.

Problem

Long addresses, large text and device constraints can cause extreme horizontal overflow or render exceptions.

Suggested fix

Use Expanded/Flexible text, wrap or stack actions below 420px, add a Material ancestor, and test at 320px with large text.

User benefit

Providers can read and tap job details even when addresses or labels are long.

Before

A fixed-width row grows to the content width; the Flutter test reports a right-side overflow and a missing Material ancestor.

After

Two-line customer card on compact screens, full-width Navigate action below the text, and a constrained map card.

Confirmed by test output from mobile/test/provider_navigation_map_screen_test.dart:198-208. Source: mobile/lib/features/provider/provider_jobs_screen.dart:182-220, mobile/lib/features/provider/provider_jobs_screen.dart:857-941.

UX-06 · Async content uses a mix of spinners, skeletons and blank waits

P2

Service discovery has shape-matched skeletons, while bookings, provider home, earnings and several admin fetches use a centered spinner or direct server render without route-level loading UI.

Problem

Users experience different levels of feedback and the app can look blank during longer waits.

Suggested fix

Use skeletons for card/table shapes, named progress for matching and payment, and route-level loading/error boundaries for admin.

User benefit

Users understand whether content is arriving, what is being processed and what to do next.

Good example: mobile/lib/features/services/service_discovery_screen.dart:2280-2367. Mixed examples: mobile/lib/features/bookings/customer_bookings_screen.dart:247-269, mobile/lib/features/provider/provider_home_screen.dart:74-87, mobile/lib/features/provider/provider_earnings_screen.dart:74-99.

UX-07 · Empty queues do not always offer a useful next step

P2

Several admin queues say “No applications match” or “No cases match” and stop there. The design contract asks for an explanation plus a useful action when available.

Problem

An empty filter result can feel like a dead end, especially for a new operator.

Suggested fix

Differentiate “no records” from “no matches”, preserve filters, show a clear-filter action, and add a role-aware next step.

User benefit

Operators recover from filters and understand whether the queue is genuinely empty.

Source: admin/src/app/providers/page.tsx:73-77, admin/src/app/support/page.tsx:85-89; requirement: DESIGN.md:384-396.

UX-08 · Admin search, notifications and identity controls are not complete workflows

P1

The global search input has no form or action, the notification button has no behavior or accessible label, and the profile identity is not a menu with sign-out.

Problem

Controls imply capabilities that are not available and keyboard/screen-reader users receive little context.

Suggested fix

Wire search to a role-scoped command/search route, add labelled notification content, create a user menu, and render the real logout action.

User benefit

Operators can find work, understand alerts and safely end a session without hunting.

Source: admin/src/components/admin-shell.tsx:76-101, admin/src/auth/actions.ts:42-47. Test output also failed the expected accessible admin navigation label in admin/src/components/admin-shell.test.tsx:7-11.

UX-09 · Map status needs a text and list alternative

P1

Maps include semantic labels and a waiting state, but the tracking experience does not provide a clear list alternative for status, ETA, last update and destination.

Problem

Map movement and color are not enough for users who cannot perceive spatial motion or need a low-data path.

Suggested fix

Add a “Text view” disclosure below the map: provider status, ETA estimate, last GPS update, distance, call/chat and support actions.

User benefit

Tracking remains understandable with screen readers, reduced motion, poor network or limited map access.

Map semantics exist at mobile/lib/features/tracking/provider_live_map.dart:305-352; design requires a list/text alternative at DESIGN.md:318-328 and DESIGN.md:428-439.

UX-10 · Action density and status language need a single hierarchy

P2

Some screens use multiple prominent controls, all-caps operational labels, badges and decorative cards at the same level. This makes the next action less obvious in a service journey where speed and safety matter.

Problem

Visual emphasis is distributed across marketing-like cards rather than the current booking state and next action.

Suggested fix

Use one primary CTA per screen, reserve red for genuine danger, move telemetry to a secondary panel, and map technical statuses to stable user language.

User benefit

Customers and providers scan less and act on the right task faster.

Contract: DESIGN.md:43-58, DESIGN.md:230-238, DESIGN.md:353-372. Example: admin/src/app/page.tsx:49-70, mobile/lib/features/provider/provider_active_job_cockpit_screen.dart:379-395.

UX-11 · Admin route state is missing from the user journey

P1

No loading.tsx, error.tsx, not-found.tsx or global-error.tsx files exist under the admin app. Some data failures redirect or throw without a designed recovery screen.

Problem

A slow or unavailable backend produces a blank/error boundary instead of a clear retry and support path.

Suggested fix

Add route-level skeletons, contained fetch errors with retry, permission-aware 404/403 states, and a global fallback that preserves navigation.

User benefit

Operators keep context and know whether to retry, refresh credentials or contact platform support.

Static inventory found no route boundary files under admin/src/app. Error handling currently occurs in admin/src/features/management-api.ts:22-28 and individual pages.

UX-12 · Touch and text-size resilience is not consistently proven

P1

Many primary controls have 48px or larger targets, but nested rows, icon actions and long labels use shrink-wrapped controls. Many screens use direct fixed font sizes and truncation.

Problem

A compliant primary button does not guarantee that nested actions, labels and content remain operable at large text or 320px width.

Suggested fix

Audit hit areas separately from visual bounds, test 320px, landscape, Android font scaling and iOS Dynamic Type, and replace critical ellipsis with wrapping or expansion.

User benefit

More users can complete bookings, provider jobs and support flows independently.

Good baseline: mobile/lib/design_system/fix_button.dart:109-199. Risk examples: mobile/lib/features/bookings/customer_bookings_screen.dart:367-380, mobile/lib/features/tracking/booking_tracking_screen.dart:378-390. Requirements: DESIGN.md:109, DESIGN.md:428-445.

Motion system

Animation ideas that clarify the next state

Motion should explain cause and effect, preserve spatial context and never delay a high-value action. The target rhythm follows the design contract: 150ms press, 200ms state, 250ms emphasis and 300ms container movement, with reduced motion replacing movement by fades or immediate state changes.

MOT-01 · Calmer press and selection feedback

High

Problem: The bottom navigation uses a 400ms elastic pop on a high-frequency interaction, with no reduced-motion branch. The motion audit says high-frequency actions should be drastically reduced or still. Suggested fix: use a 100-160ms transform/opacity press response; animate selected icon only on a deliberate 150ms ease-out; use no movement for keyboard or rapid repeated selection. User benefit: navigation feels faster and less playful during urgent work.

Evidence: mobile/lib/design_system/fix_bottom_navigation.dart:28-40; contract: DESIGN.md:417-426.

MOT-02 · Booking status changes should be spatial, not decorative

Medium

Problem: Booking state changes can arrive as content swaps. Suggested fix: transition the active booking card and timeline marker with a 200-250ms directional slide or crossfade tied to the state source, then settle into the new status. Do not animate a success that has not been confirmed. User benefit: users understand what changed while scanning an active booking.

MOT-03 · Provider acceptance deserves one clear beat

Medium

Problem: Acceptance is an important state transition, but it should not be confused with a celebration. Suggested fix: use a 250ms checkmark settle, one light haptic, and a named next state. Reserve confetti or overshoot for first-time, non-urgent completion. User benefit: provider and customer get confirmation without manufactured urgency.

MOT-04 · Skeletons should match the next decision

High

Problem: Some screens already use shape-matched skeletons, while others use a generic spinner. Suggested fix: use card/table skeletons for content, a named progress rail for matching, and a blocking state for payment. Keep layout dimensions stable and stop shimmer under reduced motion. User benefit: waiting feels shorter because the user can see what is arriving.

Before

Centered spinner on a blank page, with no relationship to the next content.

After

Booking card skeleton, “Finding a verified provider” stage, cancel/help action and retry-safe timeout.

MOT-05 · Map motion should show data confidence

High

Problem: Route draw-on lasts 3 seconds and live GPS marker interpolation is still enabled under reduced motion. Suggested fix: show the route immediately or draw it in 600-900ms once, animate only trustworthy point-to-point updates, and snap to the latest point under reduced motion. Pair every movement with last-updated time. User benefit: map motion communicates update, not false precision.

Evidence: mobile/lib/features/tracking/provider_live_map.dart:84-114, mobile/lib/features/tracking/provider_live_map.dart:145-184; contract: DESIGN.md:318-328, DESIGN.md:417-426.

MOT-06 · Success, error and status use different feedback languages

Medium

Problem: Several paths use snackbars for both success and operational truth, while some success controls are simulated. Suggested fix: use a stable 150-200ms button check, inline success on the updated screen, a concise non-focus-stealing status banner, and a contained error with retry. No shake, flash or red animation for ordinary validation errors. User benefit: users can distinguish “saved”, “sent”, “accepted” and “failed”.

MOT-07 · Sheet and card transitions should preserve origin

Medium

Problem: Navigation from cards, notifications and filters can teleport between contexts. Suggested fix: use directional page transitions for deeper navigation, 200-300ms modal/sheet transitions from the trigger, and shared booking-card continuity only where the relationship is clear. User benefit: users do not lose the mental model of where they were.

MOT-08 · Reduced motion is a product requirement, not a CSS afterthought

High

Problem: Some motion primitives branch after creating/repeating controllers, and the admin media query only changes transition duration. Suggested fix: centralize the preference at each motion boundary, stop/replace loops before rendering, retain semantic status announcements, and include a reduced-motion device test matrix. User benefit: the full experience remains usable without unnecessary movement.

Motion rule Animate one or two meaningful elements per view. Do not animate every card, status dot, table row or dashboard metric. Infinite motion is for active loading or genuinely live data only. Emergency flows should use clear state changes, not celebratory motion.

01

Persistent active-booking dock

Problem: Customers must hunt between Bookings and Tracking after an active job changes. Suggestion: add a compact, persistent active-booking entry with status, provider, ETA and next event, available from every top-level customer screen. Benefit: one tap always answers “what is happening now?” P2

02

Honest provider freshness card

Problem: Trust and location data can be missing or stale. Suggestion: show verified facts with source time: “Provider location updated 2 min ago”, “Rating unavailable”, “ETA is an estimate”. Benefit: users make safer decisions and support can explain discrepancies. P1

03

Provider day timeline

Problem: Providers need to understand schedule, travel, active job and availability in one view. Suggestion: add Today with current job, next job, travel window, availability toggle and earnings summary. Benefit: fewer missed requests and less navigation. P2

04

Case evidence timeline

Problem: Proof, remarks, officer updates and resolution need one timeline. Suggestion: create a case activity stream with upload state, reviewer response, callback request and resolution reason. Benefit: citizens and support staff share the same source of truth. P1

05

Admin incident command view

Problem: Emergency and dispatch signals are spread across dashboard and booking screens. Suggestion: build a role-scoped incident queue with real event time, source, confidence, owner, next action and audit trail. Benefit: operators respond to facts rather than decorative dashboards. P1

06

Offline booking recovery

Problem: Temporary network loss can interrupt a long booking form. Suggestion: save a local draft, show what is not sent, and reconcile with the server using a stable idempotency key. Benefit: users do not lose descriptions or create duplicate requests. P1

07

Accessible text mode for tracking

Problem: Map-first tracking is not enough for every user. Suggestion: add a synchronized text view with status, ETA estimate, last update, provider contact, OTP safety instruction and support escalation. Benefit: more users can follow a service independently. P1

08

Role-aware admin command search

Problem: Global search is currently only an input. Suggestion: connect it to booking, provider, complaint, user and guarantee records with permission filtering and a recent-action history. Benefit: operators reach the right record in one action. P2

Reliability and accessibility

Make the product’s promises testable

Reliability is part of UX. A clear error state is not complete until the user can recover, and a success message is not complete until the backend has confirmed the mutation.

Release gates

  1. Admin: make npm run type-check pass, then make lint error-free and keep all Vitest tests green.
  2. Mobile: make flutter test green, including provider map, reschedule, navigation and large-text tests.
  3. Contract: add tests for provider accept, cancel, reschedule, payment, notification routing and idempotency.
  4. Browser/device: add Playwright or connected-device tests for the critical journeys, not about:blank placeholders.

State and data integrity

  • Use explicit state machines for auth, booking, provider acceptance, payment and guarantee claims.
  • Never replace unknown data with a realistic default such as rating 4.9, 48 jobs or 15 minutes.
  • Mark all stale data with source time and reconciliation state.
  • Make every simulated or fixture value visibly test-only in development.

Accessibility baseline

  • WCAG 2.2 AA contrast, visible focus, logical tab order and no keyboard traps.
  • 48dp mobile and 44px web touch targets, including nested icon and text actions.
  • Permanent labels, inline field errors, error summary focus and password-manager/autofill support.
  • Text view alternative for maps, 320px reflow, large text, screen reader announcements and reduced motion.

Reliability observability

  • Log safe diagnostic IDs for retries, timeouts, 401/403/409 and payment ambiguity.
  • Expose websocket reconnect and stale-location state in the UI, not only in logs.
  • Track completion and failure rates for booking creation, provider acceptance, cancellation, payment and support proof.
  • Add a visual system-health state for admin data sources instead of showing hardcoded “online” indicators.
Important validation limitation This audit did not run a live browser, Flutter emulator, physical device, map tile service, push notification delivery, payment gateway or production backend. Those are explicit follow-up checks, not silently assumed passes.
Priority roadmap

Sequence the work by user harm

Fix truthfulness and broken workflows before adding motion or new surface area. Each phase has a clear exit condition.

P0

Stop unsafe behavior and restore build confidence

Target: 0-2 days. Fix admin guarantee imports and type-check errors, mobile provider map overflow/Material exception, auth refresh state, provider acceptance payload, customer tracking no-ops and fabricated trust values. Exit condition: no visible action can report success without a server-confirmed state change; admin type-check and representative mobile provider tests pass.

P1

Make the main journeys dependable

Target: next 1-2 weeks. Repair booking retry/idempotency, notification invoice routing, KYC completion logic, support proof mutations, status language, earnings copy, admin auth/search/logout and route-level loading/error states. Exit condition: customer booking, provider acceptance, payment, tracking, support and admin high-risk actions have end-to-end tests and honest empty/error states.

A11Y

Prove usability across devices and assistive technology

Target: same phase. Add 320px, large text, landscape, reduced motion, keyboard, TalkBack, VoiceOver, map text alternative and screen-reader loading/error tests. Exit condition: the primary customer/provider journeys complete without clipping, hidden focus, unlabeled controls or unexplained waits.

P2

Unify the visual and motion system

Target: 2-4 weeks. Complete dark semantic tokens, restore intended font hierarchy, align provider navigation, make admin sidebar adaptive, add card/table skeletons and define fast/standard/emphasis/container motion tokens with reduced-motion branches. Exit condition: customer, provider and admin surfaces use one hierarchy with no invented defaults or high-frequency elastic motion.

P3

Add useful confidence-building features

Target: after P0-P2. Add active-booking dock, provider day timeline, case evidence timeline, incident command view, offline recovery, tracking text mode and role-aware admin search. Exit condition: each feature reduces a measured user question or operational decision, not just visual novelty.

Confirmed vs suggestion policy

Confirmed findings are supported by source inspection plus command output where available. Static findings are not claims of an observed production incident unless the command reproduced them. Suggestions and new features are intentionally framed as design or product recommendations. Possible risks require device, browser, backend, payment, push or map evidence.

Recommended follow-up test matrix
  • Flutter: 320px phone, large phone, tablet portrait/landscape, Android font scale, iOS Dynamic Type, VoiceOver and TalkBack.
  • Admin: keyboard-only route walk, narrow viewport, focus after error, loading/error/not-found, permission denied, data stale and refresh.
  • Network: offline create booking, duplicate retry, timeout, reconnect, websocket retry, map tile failure, push deep link and payment interruption.
  • Safety: expired OTP, stale GPS, emergency flow, provider acceptance conflict, support proof failure and guarantee claim permissions.
